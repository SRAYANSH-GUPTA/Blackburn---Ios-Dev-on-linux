# Linux compiles iOS; execution needs infrastructure

**The practical architecture for Blackburn is an Intel Linux build host feeding the MacBook Air’s real CoreSimulator, with separate SSH control, desktop streaming, and Flutter VM-service channels.** The inspected `xcross` source builds ARM64 iOS device binaries and ARM64 Flutter Debug Simulator bundles from Linux; it does not run CoreSimulator on Linux, and it does not currently implement an x86_64 Simulator target. Its SDK installation adapts Apple compilation inputs to upstream host compilers without translating UIKit or a simulator operating system into Linux libraries. Compose Simulator builds explicitly reject Linux and Windows in this checkout. Flutter’s existing incremental compiler and reload controller are useful foundations for a Linux-controlled remote Simulator adapter, but that adapter is additional engineering. Local macOS virtualization and Darwin translation remain substantially less predictable than using the available Mac; a very recent `vphone-linux` project claims graphical iOS on x86_64 Linux, but its Intel laptop graphics, Flutter JIT, networking, and reload behavior remain unverified. The remaining compilation work is concentrated in resource transforms and project orchestration: signing already has an independent implementation, and `gen_snapshot` is open-source Dart infrastructure.

Research date: **2026-11-04**. The primary evidence is the checkout at `/tmp/xcross-research`, commit **`ebf0f05dae3223d80eaf34b3123dec996e053f42`**, inspected against Blackburn’s `AGENTS.md`. “Verified source” below means behavior established by reading implementation or test definitions; it does not mean that the pipeline was executed. “Proposed” identifies a design or command template. “Upstream claim” identifies external project statements that were not reproduced. No real Xcode archive extraction, SDK-backed app compilation, simulator boot, remote Mac session, or iOS hot-reload session was performed during this research.

## 1. SDK surgery supplies target inputs without importing macOS execution

### Extraction is a layered archive decoder plus a selective installer

The package boundary matters. `darwin_sdk_kit` supplies archive decoding, Darwin target descriptions, SDK lookup, text-stub compatibility, and compiler/linker discovery. The `xcross` application selects Xcode files, materializes them, replaces host-sensitive resources, and writes the Swift SDK bundle. It is therefore inaccurate to attribute every installer patch to the archive extractor alone. The overall operation is **`Xcode.xip → XAR Content → pbzx chunks → odc CPIO entries → selected Darwin SDK/toolchain resources → Swift artifact bundle`**. The extractor’s own comment says it was validated with synthetic fixtures rather than a real Xcode archive; this is an important implementation maturity boundary. ([Extractor](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/archive/xcode_xip_extractor.dart#L1), [installer orchestration](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/cli/basic/sdk_command.dart#L170))

| Layer | Exact inspected behavior | Scope or limitation |
|---|---|---|
| XAR | Checks big-endian `xar!`, reads header and compressed table-of-contents length, zlib-decompresses XML, locates `Content`, computes its heap offset from header size, TOC size, and file data offset | A targeted reader, not general XAR extraction or Apple signature verification |
| pbzx | Checks `pbzx`, skips eight bytes, reads big-endian expanded/compressed chunk sizes, passes raw chunks through or decodes XZ with Dart’s archive package | A 16 MiB chunk convention and a dictionary-reset-byte workaround are implementation assumptions; the final expanded chunk is smaller than 16 MiB |
| CPIO | Parses classic ASCII `070707`/odc headers, 76-byte header fields, octal lengths/modes, dev/inode/link counts, and `TRAILER!!!` | No general binary/newc CPIO implementation |
| File selection | Keeps device and Simulator SDKs; platform frameworks/private frameworks and platform `usr/lib`; toolchain Swift, Swift-static, Clang resources and includes; selected Info.plists | Excludes toolchain `usr/bin`, Xcode GUI/IDE machinery, Simulator.app, and separately downloaded runtime images |
| Materialization | Resolves hardlink bytes, filters paths, rewrites `.tbd` payloads, writes files/modes and links, rejects traversal/cycles/case ambiguities | Selected compilation artifacts rather than a runnable Xcode installation |
| Publication | Stages, validates, backs up old installation, renames staged tree, restores old tree on failure | Structural validation does not establish every framework can compile |

The archive details are visible in the [XAR reader](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/archive/xar_reader.dart#L38), [pbzx decoder](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/archive/pbzx_reader.dart#L30), and [CPIO reader](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/archive/cpio_reader.dart#L52). The full inclusion list and extraction policy establish what is and is not installed. ([Whitelist](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_install_constants.dart#L4), [entry writing](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_archive_extraction.dart#L116), [path policy](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_archive_paths.dart#L11))

An existing `Xcode.app` directory is another supported input: the installer verifies `Contents/Developer`, traverses the allowed roots, preserves modes and link targets, and refuses source escapes. Thus the MacBook Air can donate an installed Xcode tree without Apple’s compiler executables ever running on Linux. The SDK directory and its framework interfaces are compilation inputs; **a Simulator runtime is a separate OS package**. A path named `Developer/Runtimes/...` generated by the compatibility code below does not indicate that a runtime image was copied. ([Directory extraction](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_archive_extraction.dart#L38), [Apple runtime components](https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components))

### The patches are narrower than “rewrite Apple’s SDK for Linux”

**There is no broad rewrite of Apple framework headers, modulemaps, or `.swiftinterface` text in the inspected installer.** The three post-extraction operations replace Clang builtin headers, materialize compatibility resources, and write SDK metadata. Apple target headers, modulemaps, Swift interfaces, target libraries, and text linker stubs remain Darwin inputs consumed by a cross compiler. The absence of a broad interface rewrite is particularly important: an old Swift compiler is not automatically made compatible with every newer Apple SDK. ([Post-extraction operations](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/cli/basic/sdk_command.dart#L224))

| Input or patch | What changes | Why this helps a Linux host |
|---|---|---|
| Clang builtin headers | Resolves host `swift` through symlinks, requires sibling `clang`, obtains `clang -print-resource-dir`, copies its `include` tree over extracted `usr/lib/swift/clang/include`; fallback searches selected toolchain resource directories | Aligns compiler builtin/intrinsic headers with the host Swift/Clang importer rather than mixing incompatible Apple-bundled versions |
| Toolchain stamp | Writes host Swift path/version to `xcross-host-toolchain.json`; later mismatch checks prefer the first version line, otherwise paths | Detects SDK resources prepared for another selected host toolchain and requests reinstallation |
| Swift layout compatibility | Copies canonical `usr/lib/swift/iphoneos/layouts-arm64.yaml` to `Developer/Runtimes/XcodeDefault.xctoolchain/usr/bin/layouts-arm64.yaml`; missing/empty canonical file fails installation | Supplies a layout resource expected through an Xcode-shaped path; does not install Xcode tools or an OS |
| Swift SDK metadata | `swift-sdk.json` schema 4.0 maps ARM64 device/Simulator triples to platform sysroots and target Swift/static resources, library and C++ include paths | Makes target resources discoverable to upstream Swift/SwiftPM |
| Host compatibility metadata | `info.json` schema 1.0 lists x86_64/aarch64 Linux and Windows, x86_64/arm64 macOS hosts | These are **host triples**, not a declaration of all supported target CPUs |
| Toolset metadata | Adds cross-import overlays and `-use-ld=lld` | Selects Darwin linkage behavior and overlay import support |
| `.tbd` patch | Rewrites standalone architecture token `arm64e.x1` to `arm64e`, including target lists in exports/reexports; preserves symbol names and stamps the patch version | Avoids an unrecognized architecture token in the host linker’s text-stub parser; does not rewrite machine code or emulate ARM64e |

These operations are implemented in the [host-header adapter](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_swift_toolchain.dart#L28), [metadata/layout writer](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_bundle_metadata_writer.dart#L24), [bundle patcher](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/tbd/tbd_bundle_patch.dart#L30), and [architecture rewrite](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/tbd/tbd_architecture_rewrite.dart#L1). Existing bundles receive compatibility repair and unstamped stub patches during resolution. ([Repository resolution](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/sdk/darwin_sdk_repository.dart#L11))

This checkout requires host Swift **6.4 or newer** on Linux, and its generation guard maps Xcode 27 inputs to Swift 6.4. Those are repository compatibility policies, not an independently tested release matrix. The linker resolver prefers stock LLVM `ld64.lld`, skips unsuitable proxy shims, and probes a small ARM64 iOS object; it recommends lld 19+ because of older Objective-C selector-stub defects. That probe tolerates some unfamiliar failures, so it is a heuristic rather than a full conformance test. Clang discovery respects `CC`/`CXX`, probes Darwin driver support, and derives a minimum C++ compiler estimate from `_LIBCPP_VERSION`; an older compiler can remain selected with a warning because C/Objective-C and C++ impose different requirements. ([Linux Swift requirement](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/linux/sdk/linux_swift_toolchain_host.dart#L5), [Xcode generation policy](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/xcode_swift_requirement.dart#L4), [toolchain resolution](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/toolchain/darwin_toolchain_resolver.dart#L20))

SwiftPM receives additional orchestration: the native build system instead of the unsuitable default SwiftBuild path here, disabled debug information to avoid a missing `dsymutil`, explicit SDK selection, Clang and linker sysroots, framework search paths, linker overrides, and a Foundation compatibility import header injected for Objective-C source contexts. Host compiler plugins also matter: OpenAppleMacros supplies executable replacements for selected Apple macro modules, including Previews and SwiftUI macros. SwiftDataMacros is deliberately absent because the referenced implementation is empty. These are **host plugin replacements**, not `.swiftinterface` rewriting or comprehensive macro parity. ([SwiftPM plan](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/swiftpm/build_plan.dart#L99), [macro support](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/swiftpm/open_apple_macros.dart#L11))

### Cross compilation changes the output platform rather than the host operating system

A Linux x86_64 compiler is an ELF executable running on Linux; its backend can emit ARM64 Mach-O objects. Framework headers/interfaces establish declarations and types; `.tbd` files establish link-time symbols and install names; `ld64.lld` writes Mach-O load commands and relocations. At execution, the destination Apple runtime supplies the actual UIKit/Foundation implementations. Linking a `.tbd` neither includes UIKit’s implementation nor makes its APIs execute on Linux.

The inspected Swift runner makes the required contract explicit: host `swiftc` gets target `-sdk`, `-target`, extracted Darwin `-resource-dir`, selected `ld64.lld`, cross-import overlays, disabled system-header validation, Clang sysroot and patched builtin-header paths. It manually forwards `-arch arm64`, `-platform_version`, the platform’s compiler-rt archive, dead stripping, and the Frameworks rpath because host driver defaults do not reliably infer these Darwin details. The Objective-C path uses target Clang with ARC to produce an object, then invokes `ld64.lld` directly with UIKit/Foundation, `-lobjc`, `-lc`, compiler-rt, sysroot, and platform identity. ([Swift runner](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/build/swift_runner_builder.dart#L72), [Objective-C runner](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/build/objc_runner_builder.dart#L62))

## 2. Simulator support builds ARM64 bundles and delegates execution to macOS

### CPU architecture and Apple platform are independent target coordinates

**Intel Linux host does not mean Intel Simulator output.** Both target definitions hard-code ARM64. The Simulator compiler triple has the Simulator environment suffix and its linker platform is `ios-simulator`; the device counterpart selects `ios`. ARM64 device and ARM64 Simulator binaries remain incompatible platform products despite sharing an instruction set. ([Device definition](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/target/iphone/iphone_build_platform.dart#L3-L20), [Simulator definition](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/target/simulator/simulator_build_platform.dart#L3-L20))

| Property | iOS device | iOS Simulator |
|---|---|---|
| SDK/platform | `iphoneos` / `iPhoneOS` | `iphonesimulator` / `iPhoneSimulator` |
| Versioned triple | `arm64-apple-ios<V>` | `arm64-apple-ios<V>-simulator` |
| Minimum-version option | `-miphoneos-version-min=<V>` | `-mios-simulator-version-min=<V>` |
| Linker platform | `ios` | `ios-simulator` |
| Compiler runtime | `libclang_rt.ios.a` | `libclang_rt.iossim.a` |
| Flutter engine slice | `ios-arm64` | Prefer `ios-arm64_x86_64-simulator`, then `ios-arm64-simulator` |
| Flutter output root | `build/xcross-ios` | `build/xcross-ios-simulator` |
| Flutter modes | Debug JIT; Profile/Release AOT | Debug JIT only; Profile/Release rejected |
| Compose target | Device build path | `iosSimulatorArm64`; macOS only; IPA packaging rejected |
| Execution in current run path | Physical iOS 17+ device via CoreDevice | No Linux Simulator launcher or remote destination adapter |

The engine slice directory can contain both architectures while the executable is still ARM64: runner linkage specifies `-arch arm64`, native frameworks are thinned to ARM64, and the native-assets manifest consumes `ios_arm64`. Therefore the directory name is not evidence of an x86_64 application. Simulator/device policies also separate artifact and plugin caches to avoid platform contamination. ([Flutter target policy](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/simulator/flutter/simulator_flutter_target.dart#L9-L52), [device policy](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/iphone/flutter/iphone_flutter_target.dart#L9-L47), [runner flags](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/runner_shim.dart#L139-L256), [native framework thinning](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/internal/native_asset_frameworks.dart#L241-L279))

Compose’s Linux boundary is explicit rather than inferred: Linux/Windows inject `UnsupportedComposeSimulatorCapability`, which throws “Compose iOS simulator builds are supported only on macOS.” The macOS implementation performs ad-hoc signing using Apple’s `codesign`. Changing that capability alone would still require validating Kotlin/Native, native frameworks, resources, signing, and Simulator behavior on Linux. ([Unsupported capability](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/shared/runtime/unsupported_compose_simulator_capability.dart#L7-L18), [Compose Simulator target](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/simulator/compose/simulator_compose_target.dart#L26-L68), [macOS signing](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/macos/target/simulator/compose/macos_compose_simulator_signing.dart#L17-L35))

### The CI helper proves the intended execution boundary

The workflow builds Flutter Simulator bundles on Linux and Windows using `xcross --verbose flutter build --target-platform simulator --debug`, uploads them, and uses a separate `macos-15` job to download those artifacts and invoke `.github/scripts/simulator_smoke.py`. The helper requires `uname -m` to return **`arm64`**. It validates `CFBundleSupportedPlatforms == [iPhoneSimulator]`, checks the ARM64 slice with native `lipo`, checks the Simulator build platform through `vtool`, and verifies the existing signature with native `codesign`. It inventories actual CoreSimulator runtimes using `/usr/bin/xcrun simctl`, selects one compatible with deployment minimum and SDK version, creates a device, boots it, waits for SpringBoard, installs and launches the app, checks ready/crash/process evidence, captures screenshots/logs, then shuts down and deletes its test device. ([Cross-build job](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/workflows/integration.yml#L636-L661), [Mac execution job](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/workflows/integration.yml#L1113-L1160), [smoke validation](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/scripts/simulator_smoke.py#L84-L172), [smoke lifecycle](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/scripts/simulator_smoke.py#L423-L462))

That is an existing specification for **cross-build elsewhere, execute on a real ARM64 Mac**. It is not a Linux simulator implementation, a demonstrated remote reload session, or a test result independently reproduced here. Another CI job retargets device AOT binaries to Mac Catalyst for execution; that workaround must not be read as device/Simulator interchangeability. ([AOT execution job](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/workflows/integration.yml#L767-L818))

An Apple silicon Air fits current ARM64 output. An Intel Air requires both a compatible x86_64 runtime and an x86_64 build path that this checkout lacks. Adding that path means parameterizing target definitions, Swift SDK metadata, linker architecture, engine/XCFramework slice selection, compiler-rt selection, native hooks/assets, framework thinning, artifact caches, and smoke assertions. The installer preserves included architecture files rather than intentionally stripping x86_64, but actual donor SDK contents must be inspected. Apple’s generic universal-runtime download option is not a guarantee that every latest runtime supports every Intel Mac. Apple identifies Tahoe 26 as its last Intel macOS release, making the donor model and supported Xcode version material constraints. ([Apple component management](https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components), [Apple release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26_4-release-notes), [Xcode requirements](https://developer.apple.com/xcode/system-requirements))

## 3. A remote Mac separates reliable execution from local compilation

### Use three independent channels for control, display, and reload

The proposed topology is Linux source/editor and compiler → transferred Simulator `.app` → Mac CoreSimulator. SSH carries lifecycle operations, logs, and artifact transport. VNC or Xpra carries the visible Mac desktop and input. A separate SSH TCP forward carries the Debug app’s VM-service HTTP/WebSocket endpoint. These channels solve different problems: a responsive streamed display does not establish a working reload connection, and a reachable debugger does not provide an interactive Simulator screen.

The following commands are **templates, not commands executed during this audit**. First inventory the actual Mac; choose an available Simulator UDID and replace all placeholder paths and bundle identifiers. `mac-air` denotes a configured SSH host, optionally reachable over Tailscale using ordinary macOS Remote Login/OpenSSH. Tailscale transport and Tailscale SSH’s separate server/authentication feature should not be conflated. ([Tailscale transport guidance](https://tailscale.com/docs/reference/ssh-over-tailscale))

```sh
# Inventory; the first line decides whether current ARM64 xcross output fits.
ssh mac-air 'uname -m; sw_vers; xcodebuild -version; xcrun simctl list devices available; xcrun simctl list runtimes'

# If the selected Xcode still needs its initial platform components:
ssh mac-air 'xcodebuild -runFirstLaunch'

# In the Linux Flutter project, after configuring xcross's SDK/toolchain:
xcross --verbose flutter build --target-platform simulator --debug

# Use the actual app path produced under build/xcross-ios-simulator.
rsync -a /absolute/path/Runner.app/ mac-air:/Users/MACUSER/Blackburn/Runner.app/

# Boot only if not already booted; do not erase an existing device on failure.
ssh mac-air 'xcrun simctl boot SIMULATOR_UDID'
ssh mac-air 'xcrun simctl bootstatus SIMULATOR_UDID -b'
ssh mac-air 'xcrun simctl install SIMULATOR_UDID /Users/MACUSER/Blackburn/Runner.app'
ssh mac-air 'open -a Simulator'
ssh mac-air 'xcrun simctl launch --terminate-running-process SIMULATOR_UDID com.example.runner'
```

Use the same logged-in Mac account for the helper and desktop, with an active GUI session. An SSH connection does not create an Aqua login session. Screen Sharing offers a straightforward viewer path because Apple explicitly supports third-party VNC clients. After enabling the appropriate Mac settings, `ssh -N -L 127.0.0.1:15900:127.0.0.1:5900 mac-air` lets a Linux VNC viewer use localhost port 15900. Xpra’s documented `xpra shadow ssh://MACUSER@mac-air/` is another desktop capture/control option with an appropriate macOS server package and active/unlocked display; it does not turn Simulator.app into an X11 application for `ssh -X`. ([Apple Screen Sharing](https://support.apple.com/en-ie/guide/mac-help/mh11848/27/mac/27), [Xpra shadow](https://github.com/Xpra-org/xpra/blob/master/docs/Usage/Shadow.md), [Xpra macOS packaging](https://xpra-org.github.io/xpra/Download/MacOS.html))

A WebRTC frontend is a product engineering project: a Mac producer must capture the Simulator window or desktop, encode video, manage signaling/session transport, and inject input with the needed permissions. ScreenCaptureKit and CGEvent provide components, not a ready-made remote Simulator service. `simctl io screenshot` produces test evidence; it is not a continuous interactive video/input protocol. ([ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit), [CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent))

### Linux-controlled Flutter hot reload needs an explicit remote backend

The current `xcross flutter run` implementation discovers physical USB/Wi-Fi/CoreDevice devices and describes connected iOS 17+ device operation. It has no remote SSH Simulator destination. There is also **no `xcross flutter attach` subcommand**: registered commands include build, run, doctor, precache, clean, and dap. Consequently, a proposed command such as `xcross flutter attach --remote ...` would invent functionality. ([Run command](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/composition/cli/flutter_run_command.dart#L38-L133), [command registration](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/composition/cli/flutter_command.dart#L24-L50))

The reusable part is substantial. `frontend_server_kit` runs a persistent host Dart frontend server with SDK root, incremental compilation, package configuration, target, defines, and dill output. `HotReloadController` detects changed source URIs, compiles kernel deltas, uploads them through devFS HTTP, calls `reloadSources` for the root Flutter isolate, then requests `ext.flutter.reassemble`. Restart resets the frontend, produces a full kernel, alternates dill URI, calls `_flutter.runInView`, and waits for `IsolateRunnable`. The remote backend can reuse this instead of redesigning Dart compilation. ([Frontend process](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/frontend_server_kit/lib/shared/compiler/frontend_server_session.dart#L81-L118), [reload/restart implementation](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L161-L287))

**Proposed bridge contract:** inventory and choose Mac Simulator; cross-build locally; transfer/install; launch and capture the actual VM-service URI; establish SSH forwarding; configure the local frontend server from the same project, package URIs, entrypoint, engine revision, and original Dart defines; connect `DartVmServiceClient`; construct the existing controller with a loopback endpoint; perform `initialSync()`; wire reload/restart commands; stream console/crash logs; close controller and tunnels on exit. Lifecycle and transport belong in a new backend, rather than the physical-device pairing/provisioning path. Existing configuration and VM connection APIs provide starting points. ([Reload configuration](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/hot_reload_setup.dart#L17-L85), [VM connection](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/dart_vm_service_client.dart#L41-L65))

For example, if the app reports `http://127.0.0.1:54321/TOKEN=/` on the Mac, Linux establishes the following tunnel and rewrites only the URI authority:

```sh
ssh -N -L 127.0.0.1:15432:127.0.0.1:54321 mac-air
# Linux HTTP/devFS base: http://127.0.0.1:15432/TOKEN=/
# Linux WebSocket:       ws://127.0.0.1:15432/TOKEN=/ws
```

The destination loopback is evaluated on the Mac. Preserve the authentication path, discover the actual port, account for an IPv6-only listener if present, and forward the selected VM or DDS endpoint consistently. A known endpoint avoids dependence on cross-network mDNS. **The existing controller constructs an auth-free root HTTP base**, so preserving a token through WebSocket connection alone is insufficient; devFS HTTP URL handling must also change. Current device launch disables authentication and uses port 12345, which could simplify an isolated loopback/SSH prototype, but should not be mistaken for a permanent Simulator contract. ([HTTP base and controller](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L29-L40), [devFS upload](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L368-L390), [current launch flags](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/iphone/device/core_device_launch_profile.dart#L29-L59))

The easiest interim workflow is Linux editing with sources synchronized to the Mac, and **Mac-side** `flutter attach -d SIMULATOR_UDID --debug-url='http://127.0.0.1:MAC_VM_PORT/TOKEN=/'` driven through an interactive SSH session. It moves incremental Dart compilation to the Mac, so it is a hybrid baseline rather than strict Linux compilation. A forwarded URI does not establish that stock Linux `flutter attach` can target iOS: Flutter still calls `findTargetDevice()` even with `--debug-url`. Source/engine matching and source synchronization remain necessary. ([Flutter attach implementation](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/commands/attach.dart))

Flutter reload covers Dart, not arbitrary changes to native Swift, Objective-C, Kotlin, or plugin binaries. Compose watch explicitly rebuilds, reinstalls, and relaunches because Kotlin/Native is AOT; it is not JVM class redefinition. Native Swift hot reload requires a separate injection design and must not be promised by adding SSH. ([Compose watch](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/watch/compose_watch_session.dart#L9-L33))

## 4. Local execution alternatives solve different layers and carry different uncertainty

| Architecture | What executes the application | Fit for the available machines | Judgment |
|---|---|---|---|
| Linux build + Apple silicon Air CoreSimulator | Native Mac CoreSimulator and ARM64 Simulator frameworks | Matches current Flutter Simulator output | Preferred strict-local-build direction after implementing reload adapter |
| Linux editor + Mac build/run/reload | Standard Mac tools and CoreSimulator | Works around xcross gaps, including Compose Simulator, subject to Mac inventory | Fastest baseline; compilation is hybrid/remote |
| Linux build + Intel Air CoreSimulator | Intel Mac runtime and x86_64 Simulator app | Requires compatible runtime plus xcross architecture work | Conditional; do not assume current ARM64 bundle works |
| x86_64 macOS under QEMU/KVM/OpenCore | macOS guest CoreSimulator | CPU virtualization is possible; guest graphics/runtime compatibility unresolved | Research fallback, not validated development setup |
| Darling/custom Darwin compatibility | Linux-hosted Mach/Darwin/framework translation | No demonstrated end-to-end CoreSimulator support established | Large runtime compatibility project |
| Original qemu-t8030 | Emulated iPhone SoC/ARM guest OS | Historical partial boot/userspace work | Not a completed graphical development environment |
| vphone-cli on Air | Patched iOS research VM via Virtualization.framework | Requires physical Apple silicon Mac, macOS 15+; not a macOS VM | Separate device-platform research backend |
| vphone-linux on Intel laptop | ARM64e iOS guest via QEMU TCG plus virtual graphics translation | Recent upstream graphical claim; Intel GPU and Flutter/debug path untested | Worth isolated reproduction; not a replacement promise |

### A macOS VM avoids Darwin translation but exposes graphics and aging Intel support

OSX-KVM documents a QEMU/KVM/OpenCore virtual Hackintosh and explicitly warns that the basic setup lacks graphical acceleration. Docker-OSX wraps the same kind of VM rather than making macOS or Simulator Linux processes; its inspected README still lists GPU acceleration as unfinished. Same-ISA x86_64 virtualization is distinct from ARM iOS emulation, but Core Ultra’s 22 threads do not supply an Apple-compatible graphics stack. A usable macOS desktop does not establish that CoreSimulator can boot and render UIKit/Metal correctly. ([OSX-KVM expectations](https://github.com/kholia/OSX-KVM#setting-expectations-right), [Docker-OSX capabilities](https://github.com/sickcodes/Docker-OSX#capabilities))

For this laptop, do not assume Intel Arc passthrough: it requires a usable guest driver, IOMMU isolation, and a workable host-display arrangement. No such configuration was established. A meaningful experiment must pin a macOS/Xcode/runtime combination, measure actual Simulator boot and graphics behavior, and provision RAM/storage as well as CPU. It also inherits the x86_64 Simulator build requirement absent from current xcross. Apple’s macOS license limits the relevant virtualization permission to qualifying Apple-branded hardware; owning a separate donor Mac does not satisfy the hardware condition for the Linux laptop. ([Apple macOS SLA](https://www.apple.com/legal/sla/docs/macOSTahoe.pdf))

### A Mach-O loader is the beginning of Simulator compatibility

Darling’s current README describes a Mach-O loader, a `darlingserver` implementing Mach IPC/POSIX/Darwin interfaces, reimplemented frameworks, working command-line tools, and GUI support still under development with initial Vulkan-backed Metal work. It explicitly says Xcode does not yet run. That establishes useful components, not a demonstrated CoreSimulator stack. ([Pinned Darling README](https://github.com/darlinghq/darling/blob/c7f4d853ffd9faf70c49525d69b0a51fa46da226/README.md))

The engineering blockers span dyld/shared-cache and platform behavior; Mach task/port/VM and exception semantics; pthread/workqueue/shared memory; XPC and `launchd_sim` bootstrap namespaces; host CoreSimulator services; UIKit, SpringBoard and backboardd lifecycle; IOSurface sharing and CoreAnimation composition; graphics-driver and Metal semantics; input; and signature/entitlement expectations. Some pieces exist in Darling; the missing proof is that the required behavior works together. For an x86_64 Simulator binary, matching Linux’s CPU removes instruction translation but none of these OS/graphics contracts. ARM64 Simulator output additionally requires instruction emulation or a different target build. QEMU user-mode instruction translation alone cannot provide Darwin kernel services or an iPhone SoC.

Original qemu-t8030 explores a different path: full-system iPhone emulation. Its archived project checklist reports kernel/userspace/launchd/console shell and iOS 15 support, with framebuffer, multitouch, SEP, and GPU unchecked. Booting a shell is valuable evidence of low-level progress, but not an interactive graphical Simulator. Full-system emulation must address CPU/MMU/PAC behavior, boot/security expectations, interrupts, storage, display, input, and graphics. ([qemu-t8030 checklist](https://raw.githubusercontent.com/wiki/TrungNguyen1909/qemu-t8030/Project-status.md))

### Recent vphone-linux claims warrant a distinct device-runtime experiment

**Upstream claim, not reproduced:** `vphone-linux` commit `c2dc1996c8398ddb994288a29a719360f354d268`, dated 2026-11-03, reports graphical iOS on x86_64 Linux using a `vresearch101` QEMU machine, ARM64e TCG, `reims-vgpu`, and `metal2vulkan`. The README’s sole end-to-end tested PC is an i7-14700K with roughly 62 GB RAM and an RTX 4080 SUPER. Intel GPUs are untested; documented requirements include 16 GB+ RAM, roughly 100 GB free storage, Vulkan, and root setup steps, while networking/audio are untested. Its launch-time figures are project measurements, not benchmarks for the Core Ultra laptop. ([Pinned vphone-linux README](https://github.com/YahiaAngelo/vphone-linux/blob/c2dc1996c8398ddb994288a29a719360f354d268/README.md))

This backend installs **device-platform** IPAs: its development instructions use `xtool dev build --ipa` and a guest `vphoned` service that uploads and signs apps, followed by replacement/relaunch during edits. It is not CoreSimulator and does not consume an ordinary Simulator bundle. Nothing in that development loop establishes Flutter JIT, VM-service networking, `mprotect`/debug-entitlement compatibility, or Dart hot reload. An appropriate prototype first reproduces graphics on Intel Vulkan, installs a minimal device app, tests Flutter Release rendering, and only then tests Debug/JIT and service transport. The guest uses Apple firmware/OS from IPSWs; a phrase about avoiding Apple host runtime code must not be interpreted as an Apple-code-free guest. ([Development workflow](https://github.com/YahiaAngelo/vphone-linux/blob/c2dc1996c8398ddb994288a29a719360f354d268/docs/APP-DEVELOPMENT.md))

The original `vphone-cli` instead requires a physical Apple silicon Mac with macOS 15+ and explicitly excludes macOS VM hosts. It boots an iOS research VM through Apple’s virtualization infrastructure, making it a possible secondary backend on a suitable Air, but ordinary CoreSimulator is the simpler baseline for Flutter Simulator development. Neither a simulated nor patched virtual device substitutes for validation of radios, sensors, physical timing, or all Apple service behavior. ([vphone-cli](https://github.com/Lakr233/vphone-cli))

## 5. Full Linux compilation needs bounded resource compilers and a project model

### Existing packages already cover much of compilation and signing

| Package | Relevant responsibility established by inspected paths | Boundary |
|---|---|---|
| `darwin_sdk_kit` | Archive readers, SDK lookup/metadata, target definitions, toolchain discovery, `.tbd` compatibility | No Linux UIKit or CoreSimulator runtime |
| `apple_developer_kit` | Bundle/Mach-O signing and per-bundle signing assets | Signing format support does not supply Apple-issued distribution credentials |
| `dart_mobile_device` | Physical-device transport constants/infrastructure used by the run path | Does not create a Simulator backend |
| `frontend_server_kit` | Persistent host incremental Dart compiler session | Needs a target lifecycle, VM connection, devFS sync and reload controller |
| `xcross` | CLI, SDK installation policy, Flutter/KMP build orchestration, generated runners, assets, SwiftPM integration and reload coordination | Not a general replacement for arbitrary Xcode project evaluation |

The package boundaries above follow the cited extractor, signer, run path, frontend session, and runner implementations. Their implication is that **the central compiler problem is substantially smaller than implementing Xcode or iOS**: open host tools emit Darwin binaries when given the right target resources. The remaining hard work varies with the app’s resource and dependency graph.

| Apple pipeline step | Current Linux equivalent or xcross behavior | Remaining work for broad compatibility |
|---|---|---|
| Project/scheme/build settings | xcross’s explicit Flutter/KMP model; SwiftPM integration | Arbitrary `.xcodeproj`/`.xcworkspace` graph, xcconfig expansion, build phases, scripts, embedding and platform conditions |
| Swift/Objective-C/C/C++ compilation | Upstream host Swift/Clang plus extracted SDK/resources | SDK/interface/compiler compatibility, macros/plugins, target-specific flags, unsupported project dependencies |
| Darwin linkage and binary utilities | `ld64.lld`, `llvm-lipo`, LLVM otool/objdump, install-name and strip equivalents; xcrun-style aliases | Per-tool option compatibility and unsupported linker/build-system contracts |
| Flutter Debug | Host frontend server, kernel/VM snapshot assets, prebuilt target engine | Remote Simulator lifecycle and reload adapter |
| Flutter Profile/Release | Engine-matched Linux `gen_snapshot` emits ARM64 AOT Mach-O | Audit/build exact engine/Dart revision; no Simulator AOT in current policy |
| Kotlin/Native | Cross-host compiler adaptations and KMP framework linking | Version-sensitive compiler patches; Linux Simulator path currently rejected |
| `actool` / asset catalogs | Raw `.xcassets` skipped; precompiled/ordinary resources can be supplied | Catalog semantics and compatible `Assets.car`, variants, icons, colors, appearance/scale/idiom and format handling |
| `ibtool` / storyboard/XIB | Existing `.storyboardc` copied; missing compiled storyboard references stripped, launch-screen plist fallback | Archived UIKit object graph, constraints/connections/classes, localization and storyboard manifests |
| `momc` / Core Data | No general implementation established in checkout | Model metadata, version hashes, constraints, migrations and compiled model artifacts |
| `metal` / `metallib` | Flutter fragment shaders use host `impellerc` runtime-stage output | General MSL frontend, AIR/metallib representation, platform/compiler semantics and validation |
| `codesign` | Independent Dart BundleSigner/MachOSigner for device bundles; existing ad-hoc signatures can be rehashed | Broader inputs, nested bundles and credential/provisioning policy; no-op hook shim is not signing |
| Run/debug | CoreDevice physical-device path; macOS Simulator CI helper | New remote Simulator backend; local Linux execution is a separate runtime project |

LLVM utility aliases are concrete code rather than a requirement to execute Apple binaries. Kotlin/Native support patches host-target checks and compiler classes, including enabling otherwise disabled targets, an Objective-C export workaround, and local Apple configuration dependencies. Those adaptations are version-sensitive, so the working compiler version is part of the supported configuration. ([Tool aliases](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/xcrun/cross_xcrun.dart#L398-L430), [static archives](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/tool/tool_alias_operation.dart#L176-L208), [Kotlin patches](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/kotlin_native_class_patches.dart#L14-L148))

`gen_snapshot` must be removed from the “proprietary Apple tool” category. Its source is part of Dart. xcross resolves a mode-specific compiler matching the Flutter engine, preferring shipped/cached or explicitly pinned tools before matching published artifacts and validating digests. Its AOT arguments request `app-aot-macho-dylib`, Mach-O/object paths, deployment floor, rpaths, install name, and optional debug/symbol/obfuscation output; the snapshotter emits the final dylib without a separate assembler/linker step. Debug uses kernel/VM snapshot data instead. The unresolved question is exact engine/build parity, not unavailable Apple compiler source; the separate `xcross_gen_snapshot` build internals were not audited here. ([Dart source](https://github.com/dart-lang/sdk/blob/main/runtime/bin/gen_snapshot.cc), [resolver](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/gen_snapshot/ios_gen_snapshot_resolver.dart#L54-L68), [AOT arguments](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/flutter_aot_snapshotter.dart#L112-L142))

Signing is also more complete than a shell shim suggests. `BundleSigner` inspects bundles, removes stale signatures, embeds provisioning profiles, signs deepest nested code first, seals CodeResources, and signs the root; extensions receive their own assets and entitlements. The Mach-O signer handles generated thin ARM64 binaries. Separately, staging can repair hashes in an existing ad-hoc signature after changes. That rehasher cannot create a signature for arbitrary unsigned files, and the build-hook `codesign` script that exits zero signs nothing. Real-device/App Store distribution still requires appropriate identities, profiles, entitlements, and Apple service access, regardless of what a Simulator or patched guest accepts. ([Bundle signing](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/apple_developer_kit/lib/shared/signing/bundle_signer.dart#L17-L169), [Mach-O signer](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/apple_developer_kit/lib/src/shared/signing/macho_signer.dart#L13-L74), [ad-hoc hash repair](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/apple/mach_o_code_signature.dart#L7-L139), [no-op shim](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/shared/flutter/apple_tool_shim_templates_posix.dart#L137))

### Resource avoidance is useful but does not establish tool replacement

The resource implementation skips `.xcassets`, redirects storyboards to existing compiled `.storyboardc`, and strips references when compiled content is absent; a launch screen can fall back to `UILaunchScreen`. Extension code explicitly warns about macOS-only actool/ibtool and accepts precompiled resources. These are deliberate compatibility restrictions, not hidden Linux implementations of the Apple compilers. Similarly, Flutter’s `impellerc --runtime-stage-metal --iplr` compiles its fragment-program workflow without invoking Apple’s offline `metal`/`metallib`; it is not a universal MSL compiler. ([Bundle resources](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/ios_bundle_resources.dart#L29-L101), [storyboard fallback](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/artifact/plist_storyboard_policy.dart#L14-L47), [extension restrictions](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/extensions/app_extension_resources.dart#L80-L118), [Impeller compilation](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/impeller_shader_compiler.dart#L6-L48))

Pure Swift/UIKit/SwiftUI is a plausible first-class target because the repository already compiles a SwiftUI host around a KMP framework. However, that builder takes a KMP project/framework, while Flutter uses a generated Objective-C runner. Neither establishes arbitrary native Xcode source/project support. Flutter’s SwiftPM native plugins are supported, but podspec-only native plugin source is warned about and omitted. A native target should begin with a SwiftPM-driven, programmatic UI and ordinary resources, then add project formats and resource transforms deliberately. ([Swift host](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/build/swift_runner_builder.dart#L35-L166), [Flutter plugin boundary](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/flutter_artifact_compiler.dart#L178-L222))

`xtool` is a relevant alternative for native Swift rather than proof that all Apple build tools have been replaced. At inspected revision `2af0b67447d30063235e2adb7bdc77012f431d3a`, it offers SwiftPM-to-iOS app building and cross-platform signing. Its SDK builder configures ARM64 device plus ARM64/x86_64 Simulator targets and adapts LLVM linkage/SwiftBuild behavior, including an `ld64.lld` wrapper for unsupported partial links. Signing uses RCodesign. The audited source did not establish an actool, ibtool, or general Metal compiler. Its additional target metadata also does not establish that xcross supports those targets. ([xtool SDK builder](https://github.com/xtool-org/xtool/blob/2af0b67447d30063235e2adb7bdc77012f431d3a/Sources/XToolSupport/SDKBuilder.swift), [xtool signing](https://github.com/xtool-org/xtool/blob/2af0b67447d30063235e2adb7bdc77012f431d3a/Sources/XKit/Signer/RCodesignSigner.swift))

For Metal, Apple publishes Windows-hosted tools and a separate Shader Converter that turns DXIL/LLVM shader IR into metallib. Those are useful research inputs, but a Windows binary under Wine would remain a compatibility layer rather than a native Linux compiler, and Shader Converter is not the same as an MSL frontend. Runtime source compilation, where the target API supports it, or cached donor-built metallibs can avoid some offline work. Cached Apple-produced outputs make that build hybrid. `metal2vulkan` translating guest graphics for vphone is another distinct contract: it does not by itself produce device-distributable metallibs. ([Apple Metal tools](https://developer.apple.com/metal/tools/), [Shader Converter](https://developer.apple.com/metal/shader-converter/))

### The engineering roadmap should prove one contract at a time

The first milestone is **machine and toolchain inventory**, then a reproducible Linux-built Flutter Debug Simulator app launched on an Apple silicon Air using the CI helper’s metadata, signature, runtime, ready-marker, crash-log, and screenshot checks. If the Air is Intel, establish a Mac-only baseline first and decide whether to implement the complete x86_64 target path or use a different native-Swift build tool. Record exact SDK/Xcode, host Swift/LLVM, Flutter/Dart engine, plugin, Kotlin, and runtime versions rather than treating “Linux support” as a single capability.

The second milestone is **Linux incremental compilation with remote reload**, using the explicit adapter described above. Acceptance requires a visible Dart widget update after a local source edit without reinstalling, state behavior consistent with Flutter reload, restart behavior, token-preserving HTTP/WebSocket/devFS access, deterministic source mappings, logs and reconnect/cleanup, and no hidden Mac frontend-server compilation. Test native edits separately as rebuild/reinstall operations. For Compose, preserve a working Mac Simulator baseline before replacing the unsupported Linux capability and validating all downstream stages.

The third milestone is **a bounded native Swift target and resource compiler program**. Use the Mac as an output oracle: capture command lines/tool versions for tiny fixtures, compare file trees/plists/Mach-O load commands/resource structures, and execute results on the real runtime. For actool, grow catalog feature coverage across scale, idiom, appearances, colors, icons, compression, and raster/vector forms. For ibtool, compare object archives, connections, constraints, localization, and storyboard manifests. For momc, test model/version hashes and migration behavior. For Metal, distinguish source language, AIR, container, target platform, and runtime shader behavior. One tiny accepted artifact proves only that fixture’s subset. Keep unsupported features explicit and donor-built caches labeled hybrid.

Local execution should remain a **parallel experimental track**, not a prerequisite for the useful remote workflow. For a macOS VM, demand actual Simulator rendering and input acceptance before investing in reload plumbing. For vphone-linux, first validate Intel graphics and a simple device application, then Flutter Release, then Debug/JIT/networking. For Darling, define narrow compatibility fixtures rather than assuming Xcode extraction plus a loader closes the runtime gap. This ordering allows Blackburn to deliver practical development without requiring a full Darwin/graphics port first.

## Conclusion

The MacBook Air’s most valuable roles are independent: it can donate compilation inputs, execute real Simulator workloads, and provide reference outputs for proprietary resource formats. Those roles can be reduced separately. Moving source compilation and Dart reload to Linux does not require replacing CoreSimulator; replacing CoreSimulator does not automatically solve actool or Xcode project compatibility. Treating these as separate contracts produces a tractable implementation and makes “100% Linux compilation” measurable even while execution remains on a Mac.

The strongest presently supported conclusion is therefore architectural rather than a claim of completed deployment: **xcross already contains much of a Linux-native build stack, while Blackburn needs an explicit remote Simulator adapter and a declared resource/project support envelope.** The exact donor hardware/runtime inventory and all end-to-end behavior remain validation work. This report establishes source-level behavior and concrete experiments; it does not certify real Xcode extraction, successful SDK-backed compilation, current CI results, Intel GPU virtualization/emulation performance, or a working hot-reload session on the user’s machines.
