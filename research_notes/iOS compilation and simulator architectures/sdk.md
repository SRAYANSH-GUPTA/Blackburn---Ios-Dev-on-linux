# Darwin SDK extraction and upstream Linux compiler integration

Inspected checkout commit `ebf0f05dae3223d80eaf34b3123dec996e053f42`. Findings below are verified source behavior unless marked inference or gap. No SDK installation or complete iOS compilation was run; dependency package configs are absent. Tests described are inspected test definitions, not test execution results.

## How are Xcode archives unpacked and donor files selected?

### Takeaway
The archive decoder belongs to darwin_sdk_kit; selecting files, writing the artifact bundle and most fixups belong to xcross itself. It extracts compilation inputs, not a runnable Xcode installation or Simulator OS runtime.

### Cited Findings
- `XcodeXipExtractor.validate` checks XAR header/TOC for Content; extraction locates Content and streams `PbzxReader.decode` into `CpioReader.read`. Its own library comment explicitly says the extractor has not been validated against a real Xcode.xip, only synthetic fixtures. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/archive/xcode_xip_extractor.dart#L1)
- XAR reader checks big-endian `xar!` magic, reads header size and compressed TOC length, zlib-decompresses XML, finds a named file and computes heap offset as header size + compressed TOC length + file data offset. It does not implement general XAR extraction or Apple signature validation. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/archive/xar_reader.dart#L38)
- pbzx decoder reads `pbzx`, skips 8 bytes, then processes big-endian decompressed/compressed sizes per chunk; chunks with compressed size 16 MiB or lacking xz magic pass through raw, others use package:archive XZDecoder. A decompressed size below 16 MiB marks the last chunk. It has a byte-level workaround changing an initial LZMA2 uncompressed dictionary-reset control 0x01 to 0x02 before decoding. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/archive/pbzx_reader.dart#L30)
- CPIO decoder supports only classic ASCII odc (`070707`), 76-byte headers and octal sizes/modes; it streams entries with dev/inode/nlink for later hardlink handling and stops on TRAILER!!!. No binary/newc support. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/archive/cpio_reader.dart#L52)
- Included roots are device AND simulator `Developer/SDKs`, `Developer/Library/Frameworks`, `Developer/Library/PrivateFrameworks`, and `Developer/usr/lib`; plus XcodeDefault toolchain `usr/lib/swift`, `usr/lib/swift_static`, `usr/lib/clang`, `usr/include`. Explicit descriptors are both platform Info.plists and toolchain Info.plist. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_install_constants.dart#L4)
- This excludes toolchain `usr/bin` (Apple swiftc/clang/actool/metal/etc.), Xcode GUI, most IDE machinery, Simulator.app and separately downloaded CoreSimulator runtime images. The presence of a fabricated `Developer/Runtimes/.../layouts-arm64.yaml` later does not mean a guest OS/runtime was extracted. This exclusion follows the complete inclusion whitelist. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_install_constants.dart#L4)
- `sdk install` also accepts an existing Xcode.app directory. It verifies Contents/Developer, traverses only included roots, preserves symlink targets/modes, and refuses source escapes. This lets a Mac donor supply an existing installation, but Linux must be able to read its files. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_archive_extraction.dart#L38)
- Writer resolves hardlink payloads before filtering, so an excluded sibling can supply bytes needed by an included link; it collects symlinks, rewrites TBD payloads before materialization, restores executable bits, then creates resolved links. Path policy removes Xcode.app/Contents prefix, rejects `..`, escapes, case ambiguity and cycles. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_archive_extraction.dart#L116) [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_archive_paths.dart#L11)
- Installation builds in a staging sibling, validates, then renames old install to `.previous`, publishes staged tree, restores old install on failure and cleans backup. Metadata/framework/layout checks are structural checks, not successful compilation of every framework. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/cli/basic/sdk_command.dart#L170)
- Default bundle is host configRoot/xcross/swift-sdks/xcross-darwin.artifactbundle. `current()` repairs missing compatibility layout, validates bundle, and applies unstamped TBD patches once. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/sdk/darwin_sdk_repository.dart#L11)

### Inferences
- An ordinary Xcode.xip is SDK input only; its Darwin executable tools need not execute on Linux. A Linux-hosted compiler emits ARM64 Mach-O without requiring the host CPU to be ARM64.
- Original SDK architecture files are preserved by the root whitelist: there is no lipo thinning or deletion of x86_64 Swift module/interface files in this SDK install code. Whether an actual donor provides an x86_64 simulator slice remains donor-version dependent.

### Gaps
- No real Xcode.xip was available for independent extraction validation. The checked-in synthetic end-to-end test cannot establish compatibility with every Apple archive generation. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/test/xcode_xip_extractor_test.dart#L26)
- No donor version/CPU was provided, so available simulator architectures and SDK contents are unverified.

## What patches actually make Linux Swift/Clang/lld consume the SDK?

### Takeaway
The implementation does not broadly rewrite framework headers, modulemaps, or Swift interfaces. It keeps Apple's target resources, replaces the Clang builtin headers to match the selected host Swift toolchain, adds Swift SDK metadata and layout compatibility, and rewrites an unsupported architecture token in text linker stubs.

### Cited Findings
- Post-extraction steps are exactly replaceClangBuiltinHeaders, materializeSwiftCompatibilityResources, writeSwiftSdkBundleMetadata. No header/modulemap/Swift-interface text rewriting appears in these steps. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/cli/basic/sdk_command.dart#L224)
- Header replacement resolves `swift` on PATH through symlinks, requires sibling `clang`, asks that clang `-print-resource-dir`, and copies its `include` tree over extracted `.../usr/lib/swift/clang/include`. Fallback searches selected toolchain `usr/lib/clang/<versions>/include`, then `usr/lib/swift/clang/include`. It writes `xcross-host-toolchain.json` with swift path/version. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_swift_toolchain.dart#L28)
- Host-toolchain mismatch compares first version lines, otherwise paths, and reports reinstall guidance. This is xcross's supported matching policy; it does not itself transform Swift ABI or make arbitrary newer SDK interfaces compatible with old compilers. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_swift_toolchain.dart#L145)
- LinuxSwiftToolchainHost sets minimum Swift `(6,4)` in this checkout. Separately the SDK generation guard maps Xcode 27 to minimum Swift 6.4, checked from filename before extraction and actual SDK directory afterward. Treat Xcode/Swift claims as repository support policy, not independently verified release metadata. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/linux/sdk/linux_swift_toolchain_host.dart#L5) [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/xcode_swift_requirement.dart#L4)
- Canonical `usr/lib/swift/iphoneos/layouts-arm64.yaml` is copied into `Developer/Runtimes/XcodeDefault.xctoolchain/usr/bin/layouts-arm64.yaml`; missing/empty canonical layout fails install. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_bundle_metadata_writer.dart#L24)
- `swift-sdk.json` schema 4.0 points arm64 device/simulator targets at their SDK roots, shared Swift and Swift-static resource roots, per-platform usr/lib and C++ headers (prefer toolchain libc++ over SDK fallback). `info.json` schema 1.0 declares the bundle usable by x86_64/aarch64 Linux, x86_64/aarch64 Windows, x86_64/arm64 macOS hosts. `toolset.json` adds `-Xfrontend -enable-cross-import-overlays -use-ld=lld`. These supportedTriples are HOST triples, not target architectures. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/sdk/sdk_bundle_metadata_writer.dart#L59)
- `.tbd` rewrite map is `arm64e.x1 -> arm64e`; regex replaces standalone architecture tokens everywhere, including export and reexport target fields, leaving symbol names alone. This avoids unknown-architecture parse rejection without deleting a list's last target. It only changes linker metadata, not actual machine code or device ABI. New installs patch on write, old bundles on resolve, using versioned `xcross-tbd-targets.json` stamp. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/tbd/tbd_bundle_patch.dart#L30) [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/tbd/tbd_architecture_rewrite.dart#L1)
- Repository comments attribute this to Xcode 27 new subtype and LLVM PRs #222721/#224185 and anticipate LLVM24 support. Those version-status comments have not been independently checked and should not be elevated to present-day external facts. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/src/shared/tbd/tbd_architecture_rewrite.dart#L1)
- Resolver prefers stock LLVM ld64.lld over Swift sibling linker, skips swiftly proxy shims, probes a small arm64 iOS object with `-arch arm64 -platform_version ios 13.0 13.0 -dylib`. It recommends lld19+ due ObjC selector-stub bugs in older versions. It accepts unfamiliar probe failures, so this is a capability heuristic, not full validation. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/toolchain/darwin_toolchain_resolver.dart#L20)
- Darwin clang resolver respects CC/CXX, probes Darwin driver, prefers stock LLVM and derives minimum Clang from target libc++ `_LIBCPP_VERSION /10000 -2`; too-old compiler is retained with warning because C/ObjC can still work when C++ fails. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/toolchain/darwin_toolchain_resolver.dart#L251)
- SwiftPM host integration forces native build system (Swift 6.4 default swiftbuild is unsuitable on cross host), disables debug info to avoid unprovided dsymutil, selects `--swift-sdks-path`/`--swift-sdk`, pins `-sdk` and Clang/linker `-isysroot`, adds framework paths and linker overrides. It creates a Foundation import compatibility header injected only for ObjC source contexts. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/swiftpm/build_plan.dart#L99)
- OpenAppleMacros support supplies host executable compiler plugins for FoundationModelsMacros, PreviewsMacros and SwiftUIMacros; toolchain plugins precede them for SwiftMacros, ObservationMacros, FoundationMacros. SwiftDataMacros deliberately absent because upstream implementation is empty. Pinned OpenAppleMacros revision b29af51df1f1d6d4168c73955ad247ca1d1866ad. This is plugin replacement, not .swiftinterface patching. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/swiftpm/open_apple_macros.dart#L11)

### Inferences
- Target modulemaps and interfaces are compiler input, not Linux libraries. The host compiler imports them against the Darwin sysroot; target .tbd files provide link-time symbols/install names. None of these supplies the runtime UIKit implementation on Linux.
- Host builtin-header replacement avoids mixing Apple's bundled Clang headers with a different host Swift/Clang importer. It does not imply Apple's platform framework headers become Linux-native APIs.
- A host Swift executable can support Darwin ObjC interop even though the Linux Swift runtime lacks Apple's ObjC runtime. Local non-compiling `swiftc -### -target arm64-apple-ios15.0 -parse-as-library -c <empty.swift>` on installed Swift 6.4.2 (x86_64 Linux) emitted `swift-frontend ... -enable-objc-interop`. This is observed compiler planning only; no SDK-backed UIKit compilation was performed.

### Gaps
- No complete target compilation, SDK interface compatibility matrix or macro behavior test was run. The inspected macOS-only acceptance test compiles a real Foundation ObjC probe with xcrun clang, injects arm64e.x1 into actual SDK stubs and links rewritten versions with ld64.lld; it skips when Xcode/lld unavailable, and is not a Linux compilation test. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/test/cli/sdk_tbd_link_test.dart#L1)

## What device/simulator targets and native compilation boundaries are implemented?

### Takeaway
Host Intel Linux and target Intel Simulator must not be conflated. This checkout builds ARM64 device and ARM64 Simulator targets; generic LLVM ability to emit x86_64 Darwin code is not an implemented xcross x86_64 simulator feature.

### Cited Findings
- IPhoneBuildPlatform SDK name iphoneos, platform iPhoneOS, metadata triple arm64-apple-ios, compile triple arm64-apple-ios<V>, minimum flag -miphoneos-version-min=<V>, lld platform ios. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/target/iphone/iphone_build_platform.dart#L3)
- SimulatorBuildPlatform SDK iphonesimulator, platform iPhoneSimulator, metadata triple arm64-apple-ios-simulator, compile triple arm64-apple-ios<V>-simulator, minimum flag -mios-simulator-version-min=<V>, lld platform ios-simulator. No configurable CPU parameter exists in these definitions. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/target/simulator/simulator_build_platform.dart#L3)
- Simulator metadata is omitted if Simulator platform SDK directory absent; if present it requires a versioned SDK and nonempty System/Library/Frameworks and Swift iphonesimulator resources. Its validity check does not validate an x86_64 slice. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/simulator/sdk/simulator_sdk_metadata_platform.dart#L10) [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/shared/sdk/darwin_sdk_repository.dart#L184)
- Swift runner uses host `swiftc -sdk <target SDK> -target <triple> -resource-dir <extracted usr/lib/swift> -use-ld=<ld64.lld> -Xfrontend -enable-cross-import-overlays -Xfrontend -disable-modules-validate-system-headers -Xcc -isysroot <SDK> -Xcc -isystem <patched builtin headers>`. It manually forwards lld `-arch arm64 -platform_version <ios|ios-simulator> <min> <sdk>` and target compiler-rt archive, then dead-strip and Frameworks rpath. This compensates for host clang link-driver inference/compiler-rt omissions described in code. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/build/swift_runner_builder.dart#L72)
- ObjC runner uses target clang `-target`, `-isysroot`, target framework search paths, `-fobjc-arc`, minimum-version flag, `-c`; then invokes ld64.lld directly with -arch arm64, platform version/syslibroot, UIKit/Foundation, -lobjc/-lc, target compiler-rt and rpath. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/build/objc_runner_builder.dart#L62)
- Swift app extension flags also explicitly select target Swift resource dir (code notes missing SwiftShims/mismatch without it), framework/sysroot, module name, _NSExtensionMain entry point and ARM64 platform/version. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/app_extension_builder.dart#L225)
- Default Flutter deployment target fallback 13.0; Compose minimum 15.0. SDK generation/minimum host Swift and target minimum iOS are different independent constraints. [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/ios_deployment_target.dart#L8) [source](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/compose_ios_constants.dart#L4)

### Inferences
- A pure Swift UIKit/SwiftUI executable can reuse the demonstrated compiler/linker primitives, but xcross is a Flutter/KMP build orchestrator, not a general implementation of xcodebuild's project/scheme/build-settings/resource pipeline. Source compilation feasibility does not establish arbitrary Xcode project compatibility.
- To add x86_64 Simulator builds one must parameterize target definitions and output paths/link arch, add metadata target, confirm donor x86_64 Swift/system SDK stubs, choose corresponding Flutter/Kotlin slices and compiler-rt, and test against a compatible Intel Mac runtime. Merely changing `-target` is insufficient.
- Target ARM64 simulator artifacts are suitable for a matching Apple Silicon Mac helper, while an Intel MacBook Air requires an x86_64-compatible build/runtime combination. Neither artifact executes directly on Intel Linux.

### Gaps
- No proof of exact donor SDK architecture inventory or user's Mac architecture. No claim that current/future Apple SDKs continue shipping x86_64 simulator slices.
