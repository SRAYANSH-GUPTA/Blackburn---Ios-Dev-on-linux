# xcross compilation, simulator boundary, hot reload and remaining build tools

## What does the checked-out source actually compile and execute?

### Takeaway
The inspected commit is `ebf0f05dae3223d80eaf34b3123dec996e053f42`. An Intel Linux host can cross-build ARM64 Flutter simulator applications; host CPU does not determine target CPU. The current simulator target is ARM64, while Compose simulator builds explicitly require macOS. There is no Linux simulator runner in this pipeline. All findings below are source inspection; I did not compile an app, execute CI, authenticate, or run a simulator.

### Cited Findings
- Device platform: `iphoneos`, `iPhoneOS`, Swift SDK triple `arm64-apple-ios`, versioned target `arm64-apple-ios<minimum>`, linker platform `ios`, `-miphoneos-version-min`. Simulator platform: `iphonesimulator`, `iPhoneSimulator`, `arm64-apple-ios-simulator`, versioned target `arm64-apple-ios<minimum>-simulator`, linker platform `ios-simulator`, `-mios-simulator-version-min`. These are unconditional, not host-architecture-dependent. [Device](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/target/iphone/iphone_build_platform.dart#L3-L20), [Simulator](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/darwin_sdk_kit/lib/target/simulator/simulator_build_platform.dart#L3-L20).
- Flutter simulator policy writes `build/xcross-ios-simulator`, selects `ios-arm64_x86_64-simulator` then `ios-arm64-simulator`, uses compiler-rt `libclang_rt.iossim.a`, separates plugin/artifact caches, and forbids precompiled modes. Device policy writes `build/xcross-ios`, selects `ios-arm64`, uses `libclang_rt.ios.a` and allows AOT. A fat engine directory name does NOT imply a fat/x86_64 application. [Simulator policy](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/simulator/flutter/simulator_flutter_target.dart#L9-L52), [Device policy](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/iphone/flutter/iphone_flutter_target.dart#L9-L47).
- Runner compile command is `clang -target <platform-triple> -isysroot <SDK> -F <SubFrameworks> -F <Flutter-slice> -I <Flutter-Headers> -fobjc-arc <minimum-version-flag> -c Runner.m -o Runner.o`. Link command invokes `ld64.lld` directly with `-arch arm64 -platform_version <ios|ios-simulator> <minimum> <SDK-version> -syslibroot <SDK>`, Flutter/UIKit/Foundation, `-lobjc -lc`, and `-rpath @executable_path/Frameworks`. Thus CPU and platform are distinct coordinates even for arm64 device versus arm64 simulator. [Exact commands](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/runner_shim.dart#L139-L256).
- Embedded native frameworks are explicitly thinned with `llvm-lipo -thin arm64`. The bundled native assets manifest consumes `ios_arm64`. [Native assets](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/internal/native_asset_frameworks.dart#L65-L76), [Thinning](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/internal/native_asset_frameworks.dart#L241-L279).
- `FlutterBuildOptions.validate` rejects profile/release simulator builds with a concrete error; simulator engines are treated as JIT-only. [Validation](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/models/flutter/flutter_build_options.dart#L40-L48).
- Compose simulator is `ios_simulator_arm64` / Gradle `iosSimulatorArm64`, and cannot be packaged as IPA. Linux/Windows inject `UnsupportedComposeSimulatorCapability`, whose `requireSigning()` throws `Compose iOS simulator builds are supported only on macOS.` macOS signs embedded frameworks and bundle with `/usr/bin/codesign --force --sign - --timestamp=none`. [Compose simulator](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/simulator/compose/simulator_compose_target.dart#L26-L68), [Unsupported capability](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/shared/runtime/unsupported_compose_simulator_capability.dart#L7-L18), [Mac signing](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/macos/target/simulator/compose/macos_compose_simulator_signing.dart#L17-L35).
- CI builds Flutter simulator bundles on Linux and Windows with `xcross --verbose flutter build --target-platform simulator --debug`, then uploads them. A separate job, matrix Ubuntu x64/ARM64 and Windows x64/ARM64 build-host artifacts, runs on `macos-15`, downloads these apps and calls `simulator_smoke.py`. [Cross-build/upload](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/workflows/integration.yml#L636-L661), [Mac execution](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/workflows/integration.yml#L1113-L1160).
- Smoke helper explicitly requires `/usr/bin/uname -m == arm64`. It validates plist `CFBundleSupportedPlatforms == [iPhoneSimulator]`, uses native `xcrun lipo -verify_arch arm64`, `xcrun vtool -arch arm64 -show-build` and requires `IOSSIMULATOR|7`, then `/usr/bin/codesign --verify --no-strict --ignore-resources -v`. It inventories runtimes using native `/usr/bin/xcrun simctl list --json`, selects an available compatible iOS runtime at/below installed SDK and at/above app minimum, creates its own device, boots it, waits for SpringBoard, installs and launches. It observes real macOS process PID/launchd job, checks crash markers/reports and ready marker, captures screenshot/logs, shuts down and deletes the created device. [Metadata/validation](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/scripts/simulator_smoke.py#L84-L172), [Execution](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/scripts/simulator_smoke.py#L423-L462), [Evidence](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/scripts/simulator_smoke.py#L364-L393).
- AOT device CI does not prove Simulator device-binary interchangeability: another job explicitly retargets iOS ARM64 AOT Mach-Os to Mac Catalyst and runs them on Apple silicon, rather than rebuilding or claiming simulator execution. [AOT run job](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/.github/workflows/integration.yml#L767-L818).

### Inferences
- For an Apple-silicon Mac Air, the produced ARM64 simulator app is the natural remote execution artifact. If the Air is Intel, current defaults are incompatible; implement architecture as an explicit target property across SDK metadata/triples, link flags, engine and XCFramework slice selection, native assets/hooks, plugin caches, compiler-rt, framework thinning and smoke assertions, and use an Intel-compatible Xcode/runtime. Merely swapping the target triple is insufficient.
- No runtime extraction/translation implementation follows from the existence of simulator SDK support: SDK stubs/headers permit linking; macOS CoreSimulator supplies execution. CI configuration expresses intended validation, but has not been executed or independently verified during this audit.

### Gaps
- Actual installed MacBook Air architecture, macOS version, Xcode/runtime inventory and app compatibility must be measured. No supplied machine access or SDK installation was available for an end-to-end test.

## What hot-reload and native Swift scope exists, and what bridge remains to implement?

### Takeaway
`xcross flutter run` is currently a physical-device CoreDevice path, not a remote Simulator launcher. Its reload controller provides reusable incremental compilation and VM-service transport, so a Simulator/SSH adapter is an engineering extension rather than a runtime port. Flutter Dart hot reload does not reload native Swift/Kotlin code.

### Cited Findings
- `FlutterRunCommand` composes physical-device features, discovers USB/Wi-Fi/CoreDevice, and describes its operation as build/install/run on connected iOS 17+ devices; its CLI has no simulator destination/remote SSH option. [Run command](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/composition/cli/flutter_run_command.dart#L38-L133).
- Device debug launch passes `--vm-service-host=<transport-address> --vm-service-port=12345 --disable-service-auth-codes --enable-checked-mode --verify-entry-points`, optionally `--start-paused` for DAP. A forwarder publishes `ws://127.0.0.1:<local-port>/ws`. Release has no VM service, profile enables sampling profiler without hot reload. [Launch options](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/iphone/device/core_device_launch_profile.dart#L29-L59), [Port constant](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/dart_mobile_device/lib/target/iphone/device/constants.dart#L1-L7), [Forwarder](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/iphone/device/core_device_launcher.dart#L360-L385).
- HotReloadController spawns persistent host `frontend_server`, tracks changed source URIs, recompiles kernel delta, uploads via devFS HTTP, calls VM `reloadSources` on root Flutter isolate then `ext.flutter.reassemble`. Restart resets the frontend (full kernel required), alternates dill URI, calls `_flutter.runInView` and waits for `IsolateRunnable`. [Controller](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L20-L101), [Reload/restart](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L161-L287).
- Compose watch is rebuild/reinstall/relaunch, explicitly because Kotlin/Native is AOT and JVM class redefinition is unavailable. Source comment's sample timings (~133 sec Kotlin compile/~147 sec cycle) are project observations, not measurements on the user's laptop. [Compose watch](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/watch/compose_watch_session.dart#L9-L33).
- Flutter uses a generated ObjC AppDelegate/SceneDelegate/UIApplicationMain and programmatically installs FlutterViewController. This is not compilation of arbitrary app-level Xcode native sources. SPM plugins are supported; podspec-only native plugin code is warned and omitted. [Generated runner](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/runner_shim.dart#L280-L325), [Plugin support boundary](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/flutter_artifact_compiler.dart#L178-L222).
- Compose supports a SwiftUI `@main` host around a KMP framework. SwiftRunnerBuilder requires KmpProject, framework binary and Swift sources; runs host swiftc with extracted `-sdk`, ARM64 target, Darwin `-resource-dir`, framework linking, `-parse-as-library`, `-use-ld=<ld64.lld>`, cross-import overlays and disabled system-header validation. It explicitly supplies linker `-arch arm64`, `-platform_version`, compiler-rt and runtime rpath because Linux distro Clang does not synthesize the necessary Darwin driver defaults here. [Swift host builder](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/build/swift_runner_builder.dart#L35-L166), [Documented scope](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/README.md#L420-L446).
- Kotlin/Native cross-host support patches JAR bytecode: HostManager `isEnabled` always true / enabled targets all, ObjC export Swift-SR10177 workaround removed, AppleConfigurables dependency list delegates to superclass to avoid treating local SDK paths as downloadable artifacts. This is version-sensitive compiler adaptation. [Patches](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/compose/kotlin_native_class_patches.dart#L14-L148).

### Inferences
- Recommended new bridge: local `xcross flutter build --target-platform simulator --debug`; transfer `.app` preserving executable bits; Mac helper uses `simctl bootstatus`, `install`, `launch --console-pty` (or captured stdout/stderr) plus debug VM-service flags; Linux SSH local-forward connects to Mac loopback VM port. Reuse HotReloadController with forwarded DeviceEndpoint and the same local Flutter/Dart engine revision. Keep VM service on loopback and tunneled, particularly if using disabled auth. These are proposed engineering steps, not existing xcross options.
- There is no `xcross flutter attach` subcommand: registered subcommands are build/run/doctor/precache/clean/dap. Do not propose a nonexistent stock attach command. [Command registration](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/composition/cli/flutter_command.dart#L24-L50). Concrete bridge implementation sequence: compose simulator Flutter runtime, call `HotReloadSetup.buildHotReloadConfig` with local project/entrypoint and original `PackResult.dartDefines`; create DartVmServiceClient using host websocket connector and `connect(ws://127.0.0.1:<forwarded-port>/ws)`; construct HotReloadController with config/log/localHttp/VM/loopback DeviceEndpoint/host processFactory/diagnostics, then `initialSync()`, wire r/R to `reload()`/`restart()`, and close controller/SSH when done. [Config factory](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/hot_reload_setup.dart#L17-L85), [VM connect](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/dart_vm_service_client.dart#L41-L65). The underlying public `frontend_server_kit` `FrontendServerSession` spawns host Dart/dartaotruntime snapshot with `--sdk-root`, `--incremental`, `--target`, package config, defines, optional warm dill and output dill. [Compiler process](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/frontend_server_kit/lib/shared/compiler/frontend_server_session.dart#L81-L118). The current controller assumes an auth-free HTTP base `http://host:port/`; preserving a VM auth-token path requires an explicit change, even though WebSocket connect accepts a URI. [HTTP base](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L29-L40), [DevFS upload](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/hot_reload/hot_reload_controller.dart#L368-L390).
- Add separate backend interface for simulator lifecycle, SSH transfer, VM endpoint discovery, console/crash logs and termination. Do not route through USB CoreDevice pairing/provisioning. Screen streaming is independent of VM reload transport; either can fail separately.
- Easiest no-code path is Linux editing + synchronized project + Flutter/Xcode build/run on Mac, with desktop streaming; strongest local-compilation path is Linux Flutter simulator cross-build plus custom bridge. Compose should initially build/run on Mac, or require porting the rejected signing capability and then validating the entire Linux simulator compiler path.
- Pure UIKit/SwiftUI executables are plausible using the exposed Clang/Swift/linker pipeline and programmatic UI, but generic Xcode project support still needs project/settings/dependency graph evaluation, native target source compilation, resources, build scripts and extension behavior. Do not advertise xcross as a complete `xcodebuild` implementation.

### Gaps
- No simulator attach/hot-reload end-to-end test exists in the inspected CI helper: its test is build/install/launch/observe/screenshot. The proposed SSH bridge needs implementation and validation including auth-token URI handling, runtime endpoint discovery, shader/assets sync, path mapping and reconnect.
- Security design preference for the new bridge: preserve VM-service authentication and carry the complete discovered token URI through both WebSocket and HTTP devFS base (rewrite only authority to localhost SSH port). This requires changing HotReloadController's fixed root HTTP base. Existing physical-device source disables auth with `--disable-service-auth-codes`; copying that behavior is an explicit loopback-plus-SSH-only simplification, not a requirement of remote Simulator execution. Source debug flags are `--vm-service-host=<address>`, `--vm-service-port=12345`, `--disable-service-auth-codes`, optional `--start-paused`, `--enable-checked-mode`, `--verify-entry-points`; profile additionally uses `--enable-dart-profiling`, release has none. Verify these flags against the exact Flutter engine used rather than treating them as permanent Simulator API. [Current source flags](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/target/iphone/device/core_device_launch_profile.dart#L44-L59).

## Which Apple build tools are already replaced, and which remain actual gaps?

### Takeaway
`gen_snapshot` is a Dart/Flutter open-source build/packaging problem, not a proprietary Apple compiler. Signing already has an independent implementation. Asset catalogs, storyboards, Core Data models and arbitrary Metal offline compilation are not solved simply by extracting Xcode or linking against SDK stubs.

### Cited Findings
- AOT uses mode-specific host-native `gen_snapshot`, built from Flutter-pinned Dart revision by xcross_gen_snapshot on Linux/Windows; macOS uses Flutter's own shipped compiler. Resolver precedence is shipped host tool, validated cache, user pin, matching release manifest with engine/archive/executable digests checked. [Resolver contract](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/gen_snapshot/ios_gen_snapshot_resolver.dart#L54-L68).
- Snapshot arguments: `--deterministic --snapshot_kind=app-aot-macho-dylib --macho=<App> --macho-object=<object> --macho-min-os-version=<engine-floor> --macho-rpath=@executable_path/Frameworks,@loader_path/Frameworks --macho-install-name=@rpath/App.framework/App`, optional DWARF/symbols/obfuscation. It emits final dylib without assembler/linker; debug gets null snapshotter and uses kernel/VM snapshot data. [AOT arguments](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/flutter_aot_snapshotter.dart#L24-L26), [Arguments](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/flutter_aot_snapshotter.dart#L112-L142), [Debug branch](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/flutter_artifact_compiler.dart#L158-L168).
- Full device signing is Dart BundleSigner/MachOSigner (no zsign subprocess): inspect bundle, remove stale signatures, embed provisioning profiles, sign deepest nested code first, seal CodeResources, sign root; extensions get independent signing assets/entitlements. MachOSigner handles generated thin ARM64 binaries and atomically replaces files. [Bundle signer](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/apple_developer_kit/lib/shared/signing/bundle_signer.dart#L17-L169), [Mach-O signer](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/apple_developer_kit/lib/src/shared/signing/macho_signer.dart#L13-L74).
- Flutter staging repairs existing ad-hoc Mach-O page hashes after binary changes. Its code parses LC_CODE_SIGNATURE/SuperBlob/CodeDirectory and SHA1/256/384 digests; it is a rehasher, not a full signer for unsigned arbitrary files. Build-hook `codesign` shim is literally `#!/bin/sh\nexit 0\n`; do not confuse it with actual device BundleSigner or claim it creates signatures. [Refresh implementation](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/apple/mach_o_code_signature.dart#L7-L139), [No-op shim](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/host/shared/flutter/apple_tool_shim_templates_posix.dart#L137).
- App resources skip `.xcassets`; `.storyboard` is redirected to an existing adjacent `.storyboardc`. Missing compiled storyboards cause corresponding plist keys to be stripped; launch screen fallback becomes `UILaunchScreen` dictionary. Extension resources explicitly warn that actool/ibtool are macOS-only, skip raw catalogs/storyboards, accept precompiled resources and may replace storyboard controller with principal class. This is avoidance/precompilation, not replacement compilers. [Resources](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/ios_bundle_resources.dart#L29-L101), [Plist fallback](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/artifact/plist_storyboard_policy.dart#L14-L47), [Extension caveat](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/extensions/app_extension_resources.dart#L80-L118).
- Flutter fragment programs use host `impellerc --runtime-stage-metal --iplr --sl=<out> --spirv=<temp> --input=<source> --input-type=frag ...`, then remove temporary SPIR-V. This does not invoke Apple's offline `metal`/`metallib` tools and is not a general MSL/metallib replacement. [Shader compiler](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/flutter/build/impeller_shader_compiler.dart#L6-L48).
- Apple utility aliases map lipo to llvm-lipo, otool to llvm-otool/llvm-objdump, install_name_tool to llvm-install-name-tool, strip to llvm-strip, and libtool static archive handling to LLVM equivalents. [Aliases](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/xcrun/cross_xcrun.dart#L398-L430), [libtool handling](https://github.com/arxdeus/xcross/blob/ebf0f05dae3223d80eaf34b3123dec996e053f42/packages/xcross/lib/src/shared/tool/tool_alias_operation.dart#L176-L208).

### Inferences
- Practical first implementation should remove dependencies on unsupported transforms: programmatic UIKit/SwiftUI UI, ordinary bundled PNG/files, precompiled .car/.storyboardc/.momd/metallib where required, runtime Metal source compilation if acceptable, and SPM plugins. Cached remote Mac resource compilation gives broader project compatibility but violates literal 100% local builds; state that explicitly.
- For true local equivalents, treat resource formats as separate projects: inspect actool's Assets.car/theme/rendition/icon/appearance outputs using differential fixtures; inspect ibtool's keyed archived object graphs/connections/class metadata plus localized storyboard manifests; inspect momc's model metadata/version hashes/migration/constraints; inspect Metal's source language and AIR/metallib/platform ABI. Building one tiny successful artifact is insufficient evidence of general compatibility. Stage limited supported subsets and compare behavior on donor Mac Simulator.
- Native code hot reload is separate from all of these compilers; Flutter's VM incremental kernels reload Dart code, whereas Swift/Kotlin changes generally rebuild/relaunch unless a purpose-built injection mechanism is implemented.

### Gaps
- Repository-wide searches found no `momc` implementation or general `metal`/`metallib` compiler, and the cited resource paths explicitly do not compile actool/ibtool sources. This is an absence finding from the inspected checkout, not proof no external project offers partial replacements.
- xcross_gen_snapshot build-system internals were not inspected in this assigned checkout; resolver and emitted flags are confirmed, while upstream patch/build parity must be audited in its own repository.
